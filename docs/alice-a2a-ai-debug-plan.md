# alice-a2a 测试环境 AI Debug 接入方案

日期：2026-09-12
状态：首条接入已部署；实际数据覆盖和未闭环验收见 [实施记录](implementation-plan.md)。下文保留初始设计，拟议工具或目录不能据此视作已全部接入。
定位：基于 Agent Engine 的独立 AI 诊断平台，首个入口放在 alice-a2a Debug 页面。

## 1. 目标与确定的架构决策

用户在 Debug 平台点击助手图标，以自然语言查询测试环境数据、了解业务机制、追踪异常和排查问题。助手根据问题发现数据、执行查询、关联证据，展示实际处理过程并给出可核对的结论。

本方案采用用户明确选择的架构：

- AI 诊断服务直接连接 alice-a2a 数据库，不调用 Debug 的数据库查询接口。
- 传统 Debug 和 AI 助手是两个并行的数据访问入口，各自拥有后端能力。
- Debug 页面只承载 icon 和聊天界面的装配；AI 服务可独立运行，后续可提供自己的整页入口。
- 可以复用 Alice 已有管理员身份体系，但 AI 服务独立验证身份、权限和目标环境。
- 第一版完成只读查询、答疑和诊断。修改业务数据、重跑任务、重启服务、发布配置另行设计。

“查看所有数据”指覆盖当前管理员获准访问的业务与运行数据，而非每次把整个数据库送给模型。通过数据目录发现、按需查询和分页读取覆盖范围，通过字段、行及环境授权界定访问边界。

## 2. 整体架构

```text
传统入口
  Debug 页面 ── 原有 Go Debug 后端 ── Alice 数据库 / 服务

AI 入口
  Debug 页面内的 icon，或独立 AI 页面
                 │
                 ▼
  站点网关：静态资源、TLS、同源路由
                 │
                 ▼
  独立 AI 诊断服务（Node + Agent Engine）
    ├─ 管理员认证与数据权限
    ├─ 聊天协议、页面上下文和诊断会话
    ├─ 模型、Skill、工具编排与用量
    ├─ 数据目录、业务字典、查询执行
    └─ 证据、过程展示与访问审计
                 │
       ┌─────────┼───────────┐
       ▼         ▼           ▼
  Alice 数据库  日志数据源   文档 / 指定版本源码
  只读连接      独立适配器   独立索引

  AI 服务自身存储：会话、Run、事件、用量、查询审计与证据
  使用独立 PostgreSQL 数据库，与被诊断的业务数据隔离。
```

浏览器只请求 AI 服务公开的聊天和证据接口。模型只看到工具契约与获准返回的数据，不接触数据库连接串、管理员令牌或模型凭据。

传统 Debug 的不可用不应导致 AI 诊断后端无法查询数据；但双方仍可能共享数据库、身份服务等基础设施，不能据此承诺故障完全隔离。

## 5. 数据源和业务字典

### 5.1 连接组织

以逻辑数据源 ID 配置连接，例如 `alice-biz`、`alice-agent`，由服务端映射到实际实例、数据库、Schema 和只读角色。模型不能指定任意地址或提供连接串。

Biz 和 Agent 是逻辑数据域。现有本地配置允许它们落在同一实例和数据库，测试环境物理拓扑尚未核实，不能预设一定有两个独立数据库。

- 同库、已授权关系可以执行受控联表查询。
- 异库关系通过分别查询后在诊断服务内按明确关联键合并。
- 第一版不引入联邦数据库、任意远程连接或全库复制。
- 多源结果分别标注读取时间，不声称具备跨库事务一致快照。
- 若使用只读副本，结果需要标明副本及可获得的复制延迟；不能把延迟记录当作业务对象不存在。

### 5.2 数据目录与业务含义

自动从获准访问的表、视图和系统目录读取字段类型、约束、索引、注释，生成版本化目录。目录本身也按权限过滤。

另维护一份业务字典，补齐数据库结构无法表达的知识：

- 表和字段的业务用途、状态枚举及时间单位。
- 管理员、被查询用户、Agent、会话、消息、任务和 Trace 的 ID 含义。
- 有外键和无外键的关联规则，关联的唯一性及一对多关系。
- 软删除、失败、取消、处理中、投递完成等状态的判断依据。
- 字段可见性、正文是否可送入模型、默认时间范围及推荐查询路径。
- 对应迁移、代码版本或维护责任人。

目录发现负责覆盖，业务字典负责解释。缺少明确关联时，助手应报告不确定性或索取线索，不根据字段同名直接断定是同一对象。

## 6. 工具设计

下列名称均为拟议接口，当前尚未实现。工具由诊断服务通过 Binding 装配，`sideEffect` 声明为 `read`，同时由真实执行器和数据库权限落实只读。

### 6.1 通用数据工具

| 工具 | 主要输入 | 主要输出 |
| --- | --- | --- |
| `data.catalog` | 业务关键词、目录分页 | 可访问的数据源、表/视图、用途与匹配依据 |
| `data.describe` | 逻辑数据源、表/视图 ID | 字段、索引、约束、关联和状态解释 |
| `data.query` | 逻辑数据源、单条查询、参数 | 有界结果、字段说明、查询 ID、耗时、读取时间与截断标记 |
| `evidence.read` | 证据 ID、服务端游标 | 已授权证据详情或下一页，包含来源与失效状态 |

采用“少量通用工具 + 常见业务工具”，不要求每增加一张表就新增工具。

`data.query` 第一版建议支持经过验证的 PostgreSQL SELECT，包括必要的联表、聚合和只读 CTE。模型先查目录，再生成查询；参数值与 SQL 分离。查询能力属于 Alice 诊断适配器，不扩大 Engine 核心接口。

### 6.2 查询执行约束

查询流程为：身份与环境校验 → 解析 SQL → 校验关系、字段和函数 → 执行只读事务 → 结果投影 → 记录证据与审计。

- 使用真正受限的数据库角色：授权指定关系/视图的 SELECT，不授予写、建表、角色切换或可执行任意代码的权限。
- 使用 PostgreSQL 语法解析器验证单条语句及整个语法树；不能仅检查字符串以 SELECT 开头。
- 拒绝修改型 CTE、锁定读、SELECT INTO、COPY、DDL、DML、角色/会话设置及未开放函数调用。SELECT 也可能通过函数产生副作用，函数和过程权限需一并收敛。
- 固定服务端连接与搜索路径；校验所有查询关系，不能通过其他 Schema、扩展或用户自定义函数绕过范围。
- 设置只读事务、查询超时、连接并发和输出字节上限。LIMIT 只限制返回结果，不能替代扫描成本控制。
- 大范围查询要求时间范围或选择条件；必要时只做 EXPLAIN 预检，不自动执行 EXPLAIN ANALYZE。
- 取消和超时必须传播到实际数据库查询；连接状态不明确时销毁连接，不能把仍在执行的查询放回池中。
- 查询错误向模型返回可修正的错误类别和安全字段信息，底层连接信息留在受控服务日志中。

首轮联调的建议起点：单次查询 5 秒、最多向模型返回 100 行/64 KiB、每轮最多 10 次数据查询。具体值由表规模和测试环境容量验证后配置，不作为已验证的性能承诺。达到限制时明确说明范围，不能把部分结果说成全量统计。

### 6.3 业务工具和其他数据源

通用查询之外，优先封装 `diagnosis.message`、`diagnosis.task`、`diagnosis.modelCall` 等常见查询，把关联路径做成可测试的代码。它们同样直连数据库，不包装现有 Debug HTTP 接口。

数据库外的数据独立接入：

- `logs.search`：连接测试环境实际日志存储，按服务、时间和 Trace 查询。
- `docs.search` / `docs.read`：读取版本化业务说明、运行机制及排障文档。
- `code.search` / `code.read`：只查询明确指定的源码版本；用部署版本关联，不能把本地最新代码视作测试环境正在运行的代码。

没有某个数据源时，目录明确标记未接入，回答说明证据缺口。第一版不开放任意 shell、任意 URL 请求或服务器文件遍历作为兜底工具。

## 7. 使用场景与诊断 Skill

### 7.1 消息没有回复

入口：选中消息后点击“询问助手”，或输入用户/消息线索。

路径：确认对象 → 查消息和会话 → 查关联执行记录 → 定位模型/工具错误 → 查投递状态 → 必要时查日志。

回答应指出链路停在哪一段、对应记录和时间。没有执行记录不等于模型失败；需要继续区分未触发、记录未落库、留存过期和查询范围不完整。

### 7.2 回复慢或用量异常

路径：固定时间窗口 → 取得可用阶段时间和调用次数 → 检查重试、工具耗时、Token 记录 → 对照同类请求。

阶段时长、Token 或费率缺失时明确显示缺失，不把推测值当作实际测量值；费用只在有对应模型费率和可靠用量时计算。

### 7.3 任务卡住或结果缺失

路径：任务与状态流转 → 最近成功步骤 → 后续依赖/调度记录 → 错误与输出对象 → 检查完成和投递是否一致。

只给出排查结果与建议。第一版不会自动重试任务、补数据或修改状态。

### 7.4 为什么系统会产生这种行为

路径：定位实际调用 → 读取生效配置、Prompt 引用/版本 → 查对应记录 → 对照对应版本文档或源码。

区分运行时事实与代码推断，特别区分“当前配置”和“问题发生时的配置”。缺少历史配置记录时不能用现值倒推当时状态。

建议首批 Skill 为 `message-diagnosis`、`task-diagnosis`、`behavior-explanation`。Skill 组织检查顺序、证据要求和答复方式，不授予工具权限；关键范围限制由服务端和执行器落实。

## 8. 页面上下文、身份与会话

### 8.1 独立身份验证

现有 Alice 远程工作台使用具名管理员，Debug 工具要求 superadmin。第一版 AI 诊断服务建议沿用同等准入标准，再按数据域收敛具体可读范围。

AI 服务直接对接同一身份源或验证其签发的专用短期凭证，不信任浏览器自填的 adminId、role 或环境。站点网关可提供同源路由，但不能仅以“流量来自内网”证明用户身份。

将可信管理员映射到 Engine 的 `VerifiedPrincipal`。被查询的业务 userId 是诊断对象，不是当前操作管理员，不能拿它替换 principal。

认证凭据不写入 Run.context、提示词、工具参数或事件。每次读取会话、证据及执行查询时重新执行适用的数据权限检查，历史结果也不能绕过撤权。

### 8.2 上下文接入

页面提供线索：当前页面、所选用户/会话/消息/任务/Trace、时间范围。AI 服务校验后建立诊断范围：

```json
{
  "environmentId": "staging",
  "scopeId": "opaque-server-issued-id",
  "subject": { "type": "message", "id": "selected-message-id" },
  "timeRange": { "from": "ISO-8601", "to": "ISO-8601" },
  "catalogVersion": "versioned-catalog-id"
}
```

以上为拟议业务数据格式，不是当前 SDK 新增类型。环境由部署与服务端授权确定；页面候选 ID 和时间窗口经过校验后才进入范围，外部字段不自动变成权限。

Engine 的 `RunInput.context` 是可信宿主上下文，供授权和 Binding 使用，**不会自动进入模型提示词**。因此需要分开处理：

- 将校验后的范围放进 Run.context，让每个工具执行器使用。
- 通过受控的 `diagnosis.context` 工具或宿主生成的安全上下文摘要，让模型知道当前正在查看什么。
- 相对时间“最近一小时”在受理时解析为固定窗口，重试不重新解释时间。
- 一轮受理后冻结范围；用户切换对象只影响下一轮，正在执行的查询继续使用原范围。

标准 chat-server 目前缺少页面上下文契约。建议补一个可选的宿主解析扩展点（暂名 `resolveRunContext`），由宿主把不透明范围引用解析成可信上下文；名称和参数在 API 评审时确定。禁止把浏览器提交的任意 context 原样传给 Engine。

同一请求 ID 的重投必须复用已受理范围及解析结果，不能随当前页面重新解析造成业务 Hash 改变或查错对象。旧接入不传范围时保持现有行为。

### 8.3 对话与入口体验

- 全局 icon 打开助手，支持从当前业务对象预填问题；只打开或预填不自动执行查询。
- 显示当前环境与诊断对象，并允许用户显式切换或清除对象。
- 切换环境新建诊断会话；切换管理员销毁前端实例并清除本地会话引用。
- 同一会话保留上下文，但数据库事实每次按问题需要重新查询，避免把历史答案当作实时数据。
- 独立页面可以完成选择对象、提问和读取证据，不要求先访问传统 Debug。
- 模型选择只列出管理员可用且获准处理这些数据的模型；有视觉配置时可附截图，未接入 ASR 时麦克风禁用。

## 9. 回答、过程和证据

一次完整回答包含：结论、证据、尚未确认的部分和建议下一步。数据不充分时可以追问对象或时间范围，不补造故障原因。

处理过程展示真实工具活动，例如“查看消息记录”“查询关联调用”“搜索错误日志”；展示命中数量、耗时和安全摘要，不显示私有思考正文。

每项证据至少有以下信息：

| 字段 | 含义 |
| --- | --- |
| evidenceId / queryId | 服务端生成的证据和查询标识 |
| environment / source | 环境和逻辑数据源 |
| object references | 相关记录及主键，按权限决定可见字段 |
| query scope | 时间范围、筛选条件、目录/语义版本 |
| observedAt | 实际读取时间 |
| completeness | 是否截断、分页、缺源或存在副本延迟 |
| summary / detail URL | 安全摘要与诊断服务自己的详情入口 |

模型用受控结果生成答案；大型结果先裁剪和摘要，正文详情按需读取。已有 `describeProcess` 只控制过程摘要，不能代替数据返回前的字段过滤；未经处理的工具输出可能进入模型上下文及 Engine 存储，过滤必须发生在工具返回之前。

证据详情由 AI 服务独立提供；可附传统 Debug 深链接作为便利入口，但独立核对证据不能依赖它。结果游标须与管理员、范围及查询绑定，不允许修改游标跨对象取数。

证据读取应区分“当时保留的有界结果”和“重新查询的最新结果”；重新查询产生新读取时间及证据版本，不伪装成历史快照。留存期限、正文持久化范围与失效提示在部署配置中明确，不无限保存原始消息和日志。

## 10. 测试环境部署

### 10.1 部署位置与现有发布入口

首选部署在 Alice 现有测试服务器上，通过 Docker Compose 增加独立诊断服务和专用 PostgreSQL 容器。部署前检查资源容量与数据库网络可达性，容量不满足时再将诊断服务迁至独立机器；独立服务不要求独占服务器。

当前 Alice 发布真值是 `deploy/lingjing/docker-compose.yml`、相关发布覆盖文件和 `scripts/deploy-staging.sh`。测试环境现有脚本按已提交 Git 版本准备发布，在测试服务器构建镜像，不要求先经过 GitHub Actions、公共 npm 或 Harbor。`deploy/remote/` 已标记为历史资料，不从中复制旧拓扑和配置。

| 部署对象 | 建议放置方式 | 网络与持久化 |
| --- | --- | --- |
| `diagnostics` | 新增独立 Node 容器 | 只经站点网关提供访问；内网连接数据库、身份、模型及日志服务 |
| `diagnostics-db` | 新增专用 PostgreSQL 容器 | 独立持久化卷与账号，保存 Engine 和诊断记录 |
| Alice 数据库 | 继续使用现有实例 | `diagnostics` 使用专用只读角色直连，不为此增加公网数据库端口 |
| Debug icon / 页面适配 | 随 Debug 前端部署 | 挂载入口、页面对象线索、主题与登录生命周期衔接 |
| 聊天资源 / 独立 AI 页面 | 建议由 `diagnostics` 提供版本化静态资源 | 同一套前端服务浮窗和整页，方便独立升级 |

容器名称是建议名称，尚未添加到 Compose。模型调用已配置的模型服务，不要求在测试服务器部署模型推理进程。

### 10.2 网关与入口

路由建议如下，路径在实施时统一确认：

```text
测试站点网关
  ├─ 原有 Debug 路径          → debugd
  ├─ /ai-debug/               → diagnostics：独立 AI 页面
  ├─ /ai-debug/assets/        → diagnostics：版本化聊天资源
  └─ /api/ai-debug/           → diagnostics：聊天、上下文和证据接口
                                  ├─ Alice 数据库：只读
                                  ├─ diagnostics-db：读写
                                  └─ 身份、模型与其他证据来源
```

AI 路由由网关直接转发，不进入 Go Debug 的数据查询处理链。网关转发不替代 AI 服务自身认证。

推荐 Debug 只集成轻量挂载模块，聊天资源由诊断服务统一提供。资源使用版本化 URL，加载入口采用可更新的缓存策略；发布记录关联前端资源版本与服务端版本。若实际集成选择将 Chat UI 打入 Debug 自身资源，则升级 Chat UI 时必须一并更新 Debug 前端，不能声称只发布诊断服务就会生效。

### 10.3 Git 双仓管理与版本锁定

源码以 Git 为真值，两个仓库职责保持独立：

| 仓库 | 管理内容 |
| --- | --- |
| `agent-engine` | 通用引擎、Chat UI/Core/Server、SDK、通用契约及测试 |
| `alice-a2a` | 诊断宿主、数据库工具、业务字典、Skill、icon 装配、部署和环境非密配置 |

在 Alice 仓库内提交一份 Agent Engine 来源锁定清单，暂定位置为 `diagnostics/agent-engine.lock.json`。该文件是待实现的构建契约，不是现有 SDK API。

清单至少记录 Agent Engine 的仓库标识、完整 Git commit，以及构建所需的包集合；构建使用该提交中的依赖锁文件，并固定 Node、包管理器和基础镜像版本。外部仓库认证由发布系统提供，不写入清单或镜像。

- 发布 Alice 的某个 commit，就同时确定了它使用的 Engine commit。
- 分支或 tag 可以作为操作者选择版本的入口，但正式构建前必须解析、验证并记录完整 commit。
- 不让 Alice 与 Engine 各自自动跟随最新分支，不在运行中的容器里持续 git pull。
- 未提交工作区改动不自动进入发布；本地联调可以使用开发包，正式部署必须切换成已锁定的来源。
- 当前 Alice 部署脚本中的 `--engine-ref` 指的是其发布引擎版本，不是本项目的 Agent Engine SDK 版本。不得复用或混淆该参数，SDK 版本由独立清单管理。

### 10.4 无内部包仓库时的构建流程

第一版可以直接按 Git commit 构建 SDK 安装包，不必等待公共 npm 或内部制品库上线：

```text
选择并解析 alice-a2a 的完整 commit
    ↓
从该提交读取 Agent Engine 来源锁定清单
    ↓
获取并核对对应 agent-engine commit
    ↓
将两份固定源码及构建清单准备成临时发布输入
    ↓
按现有测试发布方式传到服务器的隔离构建目录
    ↓
按锁文件安装依赖，构建 Agent Engine SDK 安装包
    ↓
诊断服务安装这批 SDK 包，构建 Chat UI 资源与 Docker 镜像
    ↓
检查制品、生成发布记录、执行诊断服务发布
```

跨仓获取可以在发布端完成，再上传固定源码快照，避免要求测试服务器持有两个仓库的长期 Git 凭据。源码准备和 SDK 打包由脚本自动完成，不手工维护两份复制的 SDK 源码，也不依赖开发者电脑上的绝对路径或软链接。

Agent Engine 当前尚未发布的内部包依赖须统一指向本次生成的安装包，不能遗漏子包后从公共仓库解析到另一版本。安装包、前端资源和最终镜像都记录摘要；镜像携带运行所需代码，运行时不再拉取源码或临时安装依赖。

后续有内部制品库时，可以将“按 commit 构建 SDK”替换为“下载该 commit 对应的已验证制品”。Alice 仍锁定来源和制品摘要，两个仓库及运行时架构无需改变。固定源码并不自动保证逐字节可复现，发布记录还需保留实际工具链与制品摘要。

### 10.5 首次部署顺序

1. 确认测试环境容量、网络、管理员身份源、模型及获准查询范围。
2. 创建 Alice 数据库专用只读角色，准备诊断服务自己的数据库账号及部署 Secret。
3. 按双仓锁定版本构建镜像和前端资源，完成对应契约与制品检查。
4. 启动 `diagnostics-db` 并配置持久化卷、备份和留存；仅对该数据库执行 Engine/诊断服务迁移。
5. 启动单实例 `diagnostics`，验证身份、只读查询、工具调用、证据与会话恢复。
6. 配置网关路由，验证独立 AI 页面，再发布 Debug icon 和页面上下文适配。
7. 使用获准测试案例完成真实模型验收，记录发布组合和实际用量。

Alice 数据源账号与 AI 自身存储账号分开。稳定 `protocolKey`、模型凭据和连接凭据通过环境 Secret 提供，不放入 Git、构建参数日志或镜像层。配置加载需要适配 Alice 现有非密/Secret 分层，不假设 Node 服务能直接复用 Go 配置加载器。

### 10.6 升级、停机与回滚

建议在现有发布流程中增加独立范围，暂名 `diagnostics-only`。当前脚本尚不支持该范围，需实现服务选择、变更检测、迁移预检、健康检查及失败处理后才能使用，不能直接照名称执行命令。

| 改动 | 发布方式 |
| --- | --- |
| Alice 查询工具、业务字典、Skill | 提交 Alice，保持 Engine 锁定版本，构建并发布诊断服务 |
| Agent Engine 核心或聊天组件 | 先提交 Engine，再在 Alice 更新来源锁定清单；验证组合后发布诊断服务及相应聊天资源 |
| Debug icon、页面上下文或挂载接口 | 发布 Debug 前端；若接口变化，再协调发布兼容的诊断服务 |
| 诊断服务数据库 Schema | 预检迁移、备份与版本兼容性，按维护流程发布 |

第一版保持同一 Engine 存储只有一个活动写入实例。先让旧实例停止受理新请求，等待活动 Run 排空或执行安全停机，再停止旧实例、确认数据库管理锁释放、执行适用迁移、启动新实例并等待就绪。不要套用业务服务的双槽位滚动更新，避免新旧实例竞争同库管理锁。

期间助手短暂不可用，Alice 业务服务和传统 Debug 不必因此重启。新版本未就绪前，前端应明确提示服务暂不可用并保留尚未确认发送的请求标识；关闭窗口不等于取消 Run。

回滚优先复用上一次保留的镜像和匹配前端资源。保持持久化卷、数据库、身份映射和密钥稳定，不通过删除数据恢复服务。若已执行不兼容迁移，旧镜像可能无法读取新存储，需要按迁移方案恢复备份或前向修复，不能承诺一键回滚且不丢记录。

正常重启保留会话、已受理 Run 和证据关联；恢复中的只读查询若需要重新执行，应产生对应的读取时间与证据，不保证动态业务数据与上次结果完全相同。

### 10.7 发布记录与验收

每次发布记录 Alice commit、Agent Engine commit、依赖锁摘要、Node/包管理器版本、基础镜像标识、SDK 包摘要、最终镜像标识、聊天资源版本、数据库迁移版本、非密配置版本及检查结果。真实 Secret 不进入记录，只关联部署侧可审计的版本标识。

需要能回答“当前测试环境运行哪一版诊断服务、哪一版 SDK、哪些查询规则”，并能定位上一次可用制品。Git 负责源码和非密配置，数据库卷与 Secret 由部署环境独立持久化。

部署验收增加：锁定清单不可用或 commit 不匹配时拒绝构建；运行镜像无需源码仓库访问；仅更新诊断服务时不重启业务；重复启动实例被管理锁阻止；服务重启后能恢复会话；前后端资源版本兼容；回滚预检能识别迁移不兼容。

发行形式保持开放。测试接入可以使用版本固定的本地包/内部制品和服务镜像；独立 ESM 可作为 icon 挂载资产。公共 npm、CLI、压缩包和安装包是否作为正式产品形态，仍另行决定。

## 11. 实施阶段与验收

以下 D0–D3 是本次接入阶段，不改变 Agent Engine 原有 M0–M3 范围，也不引入 M4/M5 的分布式调度、真实 replay 或监控产品。

| 阶段 | 交付内容 | 验收标准 |
| --- | --- | --- |
| D0 数据与身份摸底 | 确认测试环境拓扑、只读角色、身份接口、数据目录及首个诊断样本 | 指定管理员能访问约定关系；未授权访问拒绝；诊断连接不经过 Debug 查询接口 |
| D1 完整消息诊断 | icon、独立服务、会话与上下文、目录/结构/查询工具、消息 Skill、过程及证据 | 对已知“消息未回复”案例正确关联消息和运行记录，给出可核对结论；刷新能恢复会话 |
| D2 数据覆盖与排查扩展 | 关联/聚合、任务与模型调用工具、日志和版本化资料 | 任务卡住、延迟/用量异常、行为解释均有案例；缺源和截断明确展示 |
| D3 测试环境验收 | 身份撤销、并发/超时/取消、持久化恢复、用量边界、独立入口、双仓制品与发布流程 | 故障与权限用例及第 10.7 节部署检查通过；传统 Debug 查询服务停用时，独立 AI 页面仍能按授权查库 |

D1 是完整接入路径，不等于全部数据源接入完成。通过数据源清单逐项标记“已接入 / 未接入 / 无数据 / 无权限”，D2/D3 验收时明确覆盖范围。

关键验证分为三层：

1. **执行器契约**：在真实 PostgreSQL 的隔离测试数据上验证读取、联表、聚合、函数/修改型查询拒绝、超时、取消、结果上限和权限收敛。
2. **确定性诊断链路**：用固定模型与合成业务记录验证工具参数、主体/环境隔离、范围冻结、重试去重、证据引用及错误分支。
3. **已授权模型验收**：在指定测试管理员和获准样本上验证真实工具选择、问题定位和结论依据；记录真实用量，将模型推断与已知故障原因对照。

额外覆盖：没有记录、多个同名用户、历史数据过期、时间单位不一致、配置版本缺失、副本滞后、工具返回中夹带指令、退出登录后的历史读取、同一请求重投时页面已切换对象。

验收以查对对象、取到依据、准确表达不确定性和边界为准，不能仅凭聊天成功或工具接口存在就标记完成。
